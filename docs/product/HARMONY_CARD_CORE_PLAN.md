# HarmonyOS 服务卡片核心化改造方案

## 1. 结论

服务卡片要成为核心功能，首先必须保证页面展示的是系统中真实存在、真实可配置的卡片，而不是应用自己推测的状态。

本方案遵循四条原则：

- 系统添加成功前，只负责解释价值和发起添加，不预设尺寸、事件或配色。
- 系统返回后，查询真实运行卡片并以 Form ID 为单位管理。
- 不展示与真实组件不一致的模拟预览。
- 只有已经打通真实组件数据链路的配置才对用户开放。

本次继续保持纯本地实现，不申请服务器，不增加账号、联网权限或线上埋点。

## 2. 当前问题

### 2.1 模拟预览与真实卡片不一致

应用内预览是单独手写的中卡片样式，没有复用真实小、中、大服务卡片布局。它只能大致改变背景颜色，无法准确表达桌面卡片的结构、字号、留白和系统容器效果，因此删除，不再维护两套视觉实现。

### 2.2 卡片数量不可信

只依赖 `onAddForm`、`onRemoveForm` 等回调维护本地列表，会遗漏升级前已存在、回调尚未重新触发的卡片，出现“桌面已有卡片，应用显示 0 张”的情况。

HarmonyOS API 20+ 提供 `formProvider.getPublishedRunningFormInfos()`。当前工程目标 API 为 24，因此正常路径直接查询系统中属于本应用、位于桌面的运行卡片；系统查询失败时才退回本地回调记录。

### 2.3 “突出一个日子”没有真正生效

旧实现先把指定事件移到数组首位，随后时间线再次按日期排序，导致指定结果被覆盖。该功能必须修正为明确的“固定显示某个日子”：

- 小卡片：只显示所选事件。
- 中卡片：所选事件固定为主事件，其余位置按发生时间补齐。
- 大卡片：所选事件固定为主事件，其余位置按发生时间补齐。
- 所选事件被删除时：自动回退到最近事件模式。

### 2.4 “外观”实际只是配色

真实组件当前支持的是颜色体系变化，而不是布局主题变化。页面统一改称“配色”：

- `智能配色`：主色随事件紧急程度变化。
- `靛蓝`：使用固定靛蓝主色和浅色外层。
- `深色`：使用深色外层、蓝色主区域和浅色文字。

配色按钮只展示色板，不再冒充完整卡片预览。

## 3. 完整用户流程

### 3.1 首次保存

```text
保存第一个事件
  -> 保存成功承接
  -> 进入卡片中心空状态
  -> 点击“添加到桌面”
  -> 系统服务卡片页面选择尺寸并添加
  -> 返回应用
  -> 查询系统真实运行卡片
  -> 检测到新 Form ID 后显示该卡片的配置
```

用户取消系统添加时，卡片中心仍保持空状态，不记录草稿、不增加数量、不显示失败提示。

### 3.2 日常入口

只要已经存在事件，首页长期展示“桌面卡片”入口：

- 查询成功且无卡片：`桌面卡片 · 添加到桌面`
- 查询成功且有卡片：`桌面卡片 · 已添加 N 张`
- 系统查询失败：使用本地回调记录降级，不虚构不存在的卡片。

该入口不受提醒授权、首次保存引导和激活冷却状态影响。

### 3.3 无卡片状态

卡片中心仅展示：

- 服务卡片能在桌面持续显示倒计时的简短说明。
- 系统负责选择实际卡片尺寸的说明。
- `添加到桌面` 主按钮。

此时不展示卡片预览、事件模式或配色设置，因为还没有真实配置对象。

### 3.4 已有卡片状态

进入卡片中心后先查询系统运行卡片，再展示：

1. 已添加卡片列表：按真实 Form ID 和系统尺寸区分。
2. 显示内容：
   - `自动显示最近日子`
   - `固定显示某个日子`
3. 配色：
   - `智能配色`
   - `靛蓝`
   - `深色`
4. `保存并刷新`：只更新当前选中的 Form ID。
5. `添加新卡片`：重新进入系统服务卡片页面。

多张卡片互不覆盖。例如一张卡片可以自动显示最近事件，另一张可以固定显示某个生日。

### 3.5 从桌面编辑

三种服务卡片都声明 `formConfigAbility`。用户从桌面编辑某张卡片时：

```text
系统传入 Form ID
  -> 应用查询真实卡片
  -> 定位对应 Form ID
  -> 展示该卡片当前内容和配色
  -> 保存后只刷新该卡片
```

### 3.6 删除与升级

- 收到 `onRemoveForm` 时立即删除本地实例记录。
- 每次首页和卡片中心显示时用系统运行列表校准，可清理遗漏的旧记录并找回升级前卡片。
- 旧实例缺少配置字段时迁移为 `automatic + colorful`。
- 系统查询不可用时保留本地记录，不因一次查询失败清空。

## 4. 数据模型

每张真实卡片保存：

| 字段 | 含义 |
| --- | --- |
| `id` | 系统 Form ID |
| `size` | `small` / `medium` / `large` |
| `contentMode` | `automatic` / `featured` |
| `featuredEventID` | 固定事件 ID；自动模式为空 |
| `theme` | `colorful` / `minimal` / `midnight` |
| `configurationVersion` | 配置结构版本 |

不再保存“下一张卡片配置草稿”。系统没有返回真实 Form ID 前，不创建配置对象。

## 5. 实现范围

| 模块 | 改造内容 |
| --- | --- |
| `CardInstallService.ets` | 查询系统运行卡片、筛选桌面位置、映射尺寸、与本地实例校准 |
| `CountdownCardDataSource.ets` | 保存校准后的实例列表，按 Form ID 更新与刷新 |
| `CardTimelineProvider.ets` | 固定事件先占据 `entry0`，其他事件再按日期排序补齐 |
| `widget/pages/CountdownCard.ets` | 入口显式绑定 Form `LocalStorage`，根节点观察每次都变化的 `updateToken`，收到新令牌时替换渲染子树，确保 `updateForm` 的新数据强制触发可见内容重建 |
| `CardCenterPage.ets` | 删除模拟预览；无卡片只添加；有卡片才显示事件和配色配置 |
| `CountdownFormAbility.ets` | 新卡片使用安全默认值，继续维护添加、尺寸变化和删除回调 |
| `Index.ets` | 使用系统校准后的真实数量展示常驻入口 |
| `LocalizedText.ets` | 把“突出”改为“固定”，把“外观”改为“配色” |
| `entry/src/test/` | 覆盖自动排序、固定事件、固定事件删除降级和配置迁移 |

## 6. 验收标准

- 桌面已有两张本应用卡片时，卡片中心能检测到两张并显示正确尺寸。
- 用户取消添加后，数量不增加，页面不出现虚构卡片。
- 未添加卡片时不展示预览、事件模式和配色设置。
- 自动模式下，小、中、大卡片继续按发生时间显示最近事件。
- 中卡片在有足够事件时完整展示主事件和 3 条后续事件；大卡片完整展示主事件和 5 条后续事件，并将空余高度均匀分配给后续列表，不得因固定高度发生重叠、覆盖或大块留白。
- 固定事件模式下，小卡片显示所选事件；中、大卡片将其放在主位置并补齐其他最近事件。
- 新增、编辑或删除事件保存成功后，应用立即主动刷新，并在短延迟及应用退到后台时确认刷新；卡片入口通过 Form `LocalStorage` 接收新数据，根节点观察唯一版本令牌并替换渲染子树以重建可见内容，系统调用失败时继续重试。
- 两张卡片可分别保存不同固定事件与配色，互不覆盖。
- 删除固定事件后卡片自动回退最近事件，不闪退、不显示空白主区域。
- 智能、靛蓝、深色三种配色修改的是实际服务卡片，不只修改应用页面。
- 从桌面编辑卡片能定位正确 Form ID，保存后只刷新目标卡片。
- 系统查询异常时不清空已有本地记录，事件和提醒能力不受影响。
- 全部数据仍只保存在本机，不新增服务器或隐私权限。

## 7. 真机回归

- 小、中、大卡片分别添加、配置、删除和重新添加。
- 同时存在两张以上卡片时的数量、尺寸和独立配置。
- 系统添加页取消、应用冷启动返回、热启动返回。
- 桌面“编辑卡片”入口及目标 Form ID 定位。
- 中文、英文、长标题、农历长日期和字体放大。
- 跨日、跨年、固定事件删除和 `2.0.2 -> 2.1.1` 覆盖升级。

## 8. 当前实施顺序

1. 删除模拟预览和添加前配置草稿。
2. 接入系统运行卡片查询，修复真实数量和旧卡片找回。
3. 修复固定事件排序并补单元测试。
4. 重构卡片中心的空状态与已添加状态。
5. 完成单元测试、Debug 构建、签名 Release 构建和真机回归。
